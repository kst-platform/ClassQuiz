## Безопасность — что сделано и что реально защищает, а не украшает

Пользователь 22.09.2026 попросил "чтоб F12 не работала, чтоб взломать
было нельзя, чтоб данные в зашифрованном виде хранились". Разобрано так:

- **Блокировка DevTools (F12) — сознательно НЕ делаем.** Обходится тривиально
  (другой браузер, `curl`, прямой запрос к API), не останавливает никого,
  а мешает легитимной отладке и доступности. Профессиональные аудиторы
  считают это анти-паттерном ("security theater"). Настоящая защита —
  в самом API, не в браузере.
- **Пароли** — уже хранятся хешем **argon2** (`classquiz/auth.py`,
  `pwd_context = argon2` из passlib) — это современный рекомендуемый
  алгоритм, необратимый даже для нас самих. Менять не на что, это уже
  правильно сделано в апстриме.
- **Подбор пароля** — добавлено ограничение попыток входа (Фаза 2,
  `classquiz/routers/login.py`): 8 неудачных попыток на учётку → блок на
  15 минут, считается в Redis. Раньше пароль можно было перебирать сколько
  угодно раз.
- **Права администратора** — переведены с "первой строки в базе" на явный
  список `ADMINS` (см. Фазу 2) — раньше это был скрытый и непроверяемый
  механизм.
- **Удаление/смена пароля учётки** — только с повторным вводом пароля
  самого админа (см. Фазу 2).
- **Cookies сессии** — уже `httponly` + `samesite=lax` в апстриме
  (`classquiz/oauth/authenticate_user.py`) — то есть токен нельзя прочитать
  из JS (защита от кражи через XSS) и запрос с чужого сайта его не пошлёт
  (защита от части CSRF-сценариев). Тоже уже сделано правильно, не трогали.
- **Передача данных** — HTTPS обеспечивает `proxy`/Caddy из
  `docker-compose.yml` (автоматический сертификат) — доделывается в Фазе 5.
- **Данные "в зашифрованном виде"** — для базы Postgres и загруженных файлов
  правильный способ — **шифрование диска/тома на самом VPS** (провайдер
  почти всегда даёт encrypted volume, либо LUKS вручную), а не шифрование
  каждого поля в приложении. Прикладное шифрование всех данных ломает
  поиск и фильтрацию и не то, что делают "обычные программы" — они
  полагаются на шифрование диска + шифрование трафика + хеширование
  паролей, что мы и делаем. **Действие для Фазы 5**: включить encrypted
  volume у провайдера VPS при заказе сервера.
- **Не сделано, стоит добавить перед реальным вводом в эксплуатацию**:
  - rate-limit на само создание учёток (`POST /users/create`) — сейчас
    ограничен только повторный вход, не сама регистрация (спам-регистрации
    не заблокировать, хотя они всё равно попадут в очередь одобрения);
  - security-заголовки на уровне Caddy (`Content-Security-Policy`,
    `X-Frame-Options`, `Referrer-Policy`, `Strict-Transport-Security`);
  - `SECRET_KEY` в `docker-compose.yml` сейчас плейсхолдер `"TOP_SECRET"` —
    сгенерировать реальный (`openssl rand -hex 32`) при деплое, никогда не
    коммитить;
  - Dependabot у форка (унаследовал открытые PR апстрима на момент форка —
    `git branch -a` показывает ветки `dependabot/*`) — включить алерты в
    Settings репозитория `kst-platform/ClassQuiz`, чтобы получать патчи
    уязвимостей зависимостей автоматически.

имя не из списка → `username_not_in_roster`, имя из списка → `joined_game`,
повторный вход тем же именем со второго подключения → `username_already_exists`
(старая защита от дублей продолжает работать вместе с новой проверкой
ростера) → удаление группы каскадно удалило её студентов из БД.

**Грабли этого захода (не в коде платформы, в тестовом харнессе)**: при
передаче кириллицы через `curl -d "..."` в Git Bash на Windows консоль
молча заменяет буквы на `?` (байт `0x3F`) ещё до отправки запроса — из-за
этого два разных ФИО, начинающихся с русских букв одинаковой длины,
превращались в идентичную строку и один "терялся" при дедупликации. Это
не баг сервера — проверено сверкой с сырыми байтами в Postgres. Лечится
передачей JSON через файл (`curl --data-binary @файл.json`), а не строкой
в `-d`. Реальный фронтенд (SvelteKit `fetch`) всегда кодирует тело в UTF-8
и этой проблемы не имеет.

      домена, автоматический HTTPS в таком виде не работает). Теперь сайт
      задан как `{$DOMAIN:localhost}`, `docker-compose.yml` публикует
      `80`/`443` и передаёт `DOMAIN`.
- [x] `ADMINS` добавлена в переменные окружения `api`/`worker` (без неё
      панель `/account/admin` недоступна вообще никому после деплоя).

**Чек-лист на момент, когда появится VPS и домен** (по порядку):
1. Купить/арендовать VPS, направить DNS A-запись домена на его IP.
2. Клонировать `kst-platform/ClassQuiz`, ветка `kst`, на сервер.
3. В `docker-compose.yml` заполнить: `proxy.environment.DOMAIN` (реальный
   домен), `api`/`worker` env — `ROOT_ADDRESS` (тот же домен, с `https://`),
   `SECRET_KEY` (`openssl rand -hex 32`, сгенерировать заново, не
   переиспользовать тестовый), `ADMINS` (username владельца).
4. **Курица-яйцо первого админа** (см. Фазу 2): после первого запуска
   зарегистрироваться через `/account/register`, затем одобрить себя
   напрямую в БД (`UPDATE users SET approved=true WHERE username=...` —
   тем же способом, что при локальной проверке).
5. `docker compose up -d --build`.
6. Прогнать `classquiz/tests` (`pytest`) внутри контейнера или локально
   против той же БД перед тем, как пускать реальных пользователей.
7. Проверить вживую: регистрация → одобрение → вход, создание группы,
   импорт реального `.gift`-файла курса, игра с телефона по домену —
   тот же сценарий, что уже проверялся локально в Фазах 2–4, но теперь
   на настоящем HTTPS и с настоящего устройства, а не с этой машины.
8. Шифрование данных «на диске» (просили 22.09.2026) — это задача
   VPS-провайдера при заказе сервера (encrypted volume) или ручной LUKS,
   не задача самого приложения — см. `svoy-kahut/SKILL.md`, раздел
   безопасности.
